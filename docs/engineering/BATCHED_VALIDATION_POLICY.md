# Batched validation and delivery policy

Status: agreed operating policy; partitioning, shared payload publication and proof-based post-merge reuse require implementation and acceptance. This document alone changes no required workflow, check, helper, test selection or registry classification. Existing mandatory workflows and current-head review remain required until the replacement is active and its required statuses have been configured and verified.

## Deliver connected packages

Allocate approximately 60% of implementation effort to new APIs and connected runtime capabilities with complete contract validation, and 40% to existing differences and unverified contracts. This is a planning allocation across a delivery package, not permission to defer defects in the new work or manufacture API credit. Prefer one coherent package sharing dependencies over one PR per small check. Continue the existing closure matrix and remaining-work queue; do not create competing acceptance ledgers.

Before implementation, declare package scope, source pin, affected APIs/backends, dependency closure, acceptance partitions, exclusive resources, responsible owner and remaining obligations. The runtime/integration owner coordinates shared source changes. Helpers prepare independent proposals or reviews. The existing CI owner (#102, w-docs) owns shared CI/helper changes and dispatch; other workers do not edit or launch competing CI work. The runtime owner retains the separate focused poll experiment, without editing the shared validate workflow or helpers. A policy proposal grants no new publication or merge permission.

## Iterate with focused checks; gate the finished package once

During development, run declared dependency-focused regressions and genuine pinned-original comparisons for changed behavior, including cleanup and failure paths. Add newly discovered dependencies to the declaration before acceptance. If dependency impact is unknown, run the broader applicable scope rather than treating missing knowledge as proof of independence. A failed preparation blocks dependent execution, while independent checks continue and contribute to an aggregate failure. Preserve every failure and unfinished selection.

Freeze the ready package, build its final inputs, and execute one complete ready-package gate covering the mandatory matrix. Do not start a second simultaneous full validation set. A later change invalidates affected evidence according to the declared dependency graph; repeat affected checks on final sources. If the graph cannot establish a safe subset, the full gate must run again. Documentation or metadata changes also require their own guards and can invalidate executable-input evidence. Never reuse a result solely because filenames or test names appear unchanged.

Do not retry unchanged failing runs unless a specific transient cause has been demonstrated and recorded. A retry retains the original failure, diagnosis, changed environment or recovery action, and replacement run identity. A timeout, cleanup failure or out-of-memory event is a failed attempt, not an automatic reason to raise limits or claim a transient.

## Partition the full gate without changing coverage

Implement four or five independent, balanced groups from measured costs and dependency/resource boundaries. Around 20 minutes end to end is an engineering goal, including setup, build, payload materialization, execution, cleanup and aggregation; it is not a delivery promise or a larger test timeout. Serial execution remains the reference until equivalence is demonstrated.

Build once per required platform/profile/configuration compatibility boundary. Produce the smallest hash-bound immutable payload containing the required assemblies, native assets, original fixtures and manifests. Share read-only content within a compatible execution environment; materialize only needed inputs on remote runners. Give each group separate writable output, temporary paths, caches and owned processes. Do not replicate an entire approximately 7.5 GB workspace for every worker or share mutable build outputs. A Windows payload does not replace Linux artifacts, and a Debug build does not replace Release acceptance.

Bound concurrency by measured CPU, available RAM and commit headroom, I/O pressure and runner capacity. Record the limits and peak usage. Use explicit exclusive lanes for tests sharing ports, native global state, process-wide selectors, mutable fixtures or other resources that cannot safely overlap. Split or serialize those cases rather than introducing races through parallelism. Test isolation includes physical process/thread/resource cleanup, not only distinct result directories.

Compare serial and parallel execution on exactly the same commit/source tree, ordered case catalog, dependency inputs, providers, profile/configuration and supported environment. Group manifests must form an exact disjoint partition of the expected case identities for each mandatory matrix cell. Missing, duplicate, unexpected, skipped, aborted, timed-out or unexecuted cases, stale artifacts, input mutation and cleanup failures make the aggregate RED. Failures remain raw and attributable; the aggregator must not convert incomplete results into a pass. A worker startup/preparation failure is an aggregate failure even if no case ran. Keep deterministic catalog identity while allowing explicitly independent group execution order.

Measure before and after on equivalent inputs: total wall time from preparation to aggregate, setup/build/materialization/execution/cleanup times, slowest group and balance, transferred bytes, peak CPU/RAM/commit/I/O and number of complete and partial reruns. Preserve run IDs, commit/source/catalog hashes and environment. Explain non-equivalent measurements; do not claim acceleration from incomparable baselines.

## Preserve the OTP acceptance boundary

The oracle is original OTP 29.1.1 at ad05823719d77c8faee87348ea39513d4e2f99c5. Acceptance covers the full public observable contract across the advertised supported matrix: values, complete errors/stacks/metadata, options/defaults, effects, ordering/concurrency, actual GC behavior, scheduler behavior, resource ownership, cancellation, shutdown and cleanup wherever applicable. Public GC, scheduler and resource observations remain mandatory even when implementing them differently in C#/.NET.

Literal private memory layouts, absolute timings, raw process addresses and cross-VM object identities are not blanket equality requirements. This does not waive observable layout-dependent behavior, documented limits, causal ordering, timeout contracts, real cleanup, own-VM identity protocols or previously agreed raw internal cursor behavior. Use the agreed original protocol relative to each VM's own state for those internal cursors. Any comparison mapping or environment-dependent observation requires a source-justified, declared rule and retained complete raw evidence; do not invent broad normalization to hide a mismatch. Performance improvement is a separate measured claim after correctness.

Source-only audits, successful compilation, component controls and finite witnesses retain their own scopes. They do not establish full API compatibility or close all known differences. Missing platforms, backends or lifecycle partitions stay explicit. This policy changes no registry counts; record API-presence and full-contract deltas separately from new regression/component cases.

## Review-bound post-merge reuse

Post-merge deduplication is conditional on an implemented, reviewed verifier proving equivalence of tested and merged executable source trees and their declared dependencies, catalogs, build options/configuration, environment, providers, trusted immutable artifacts, every required matrix cell and final review state. Include test/tool/workflow changes in the proof when they influence acceptance. A new SHA, successful PR run or matching runtime DLL alone is insufficient. Preflight must refuse missing, stale, failed, untrusted or ambiguous evidence and fall back to the required validation.

Preserve currently configured required status identities in the reviewed migration. Suggested logical labels for new group evidence, subject to that migration, are: `validation/preflight`, `validation/full-group-1` through the configured fourth or fifth group, and `validation/aggregate`. A proven post-merge reuse decision additionally reports `validation/post-merge-equivalence`, links each original run and records every covered status/matrix cell. These are proposed logical status names, not claims that current checks exist or permission to bypass branch protection. The aggregate depends on all configured groups and gates. Until the verifier, workflow behavior and required-check configuration are active, existing full post-merge checks remain mandatory. Re-fetch final-head comments, review findings and required checks before merge; incomplete automatic review is not a clean review.

## Package progress record

For each package, report current stage, completed scope, current denominator and percent, API-presence/full-contract deltas, exact executed cases and matrix cells, remaining differences, next measurable result, responsible owner and blockers. Separate completed implementation from accepted compatibility, Linux execution from Windows compilation, and focused proof from a full gate. Keep the English changelog and immutable raw evidence, including unsuccessful attempts. Mark a checklist complete only when all its declared acceptance items and required cleanup have passed.
