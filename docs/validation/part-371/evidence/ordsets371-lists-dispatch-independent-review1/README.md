# Independent source review and final regression plan

The dynamic lists dispatch proposal changes the owning execution boundary without selecting or caching a canonical implementation. `ordsets:fold/3` tail-dispatches the actual `lists:foldl/3` entry. `ordsets:filter/2` tail-dispatches actual `lists:filter/2`. `ordsets:map/2` and `filtermap/2` retain their real non-tail source continuations (ordsets.erl543/581) during the actual selected lists call, then leave those scopes before the existing tail-usort route. Validation belongs to the selected lists implementation. Replaced lists code may accept arguments the canonical implementation rejects; the replacement HOST intentionally exercises that distinction.

The source kernels moved behind `ListFunctions.Run` preserve the preceding per-operation branches. Fold validates callback arity2 before entering the initial case on the list, invokes each callback before inspecting the next tail, and distinguishes public foldl/3 from tail foldl_1/3. Filter validates arity1 then follows comprehension true/false/bad_filter and generator-tail bad_generator paths. Map validates arity1 before the initial case and retains map/map_1 callback and malformed-tail frames. Filtermap validates arity1 then preserves true/false/{true,Value}/case_clause and filtermap_1 paths. Existing pending-continuation coalescing and source-frame utilities are unchanged.

`EnterSourceTailCall(module,function)` removes a frame only when the current top frame is a SourceWrapper with that exact module and function. Thus canonical lists kernels remove their own wrapper; they do not strip real source replacement frames. A separate zf alias path strips only its own zf SourceWrapper before calling actual filtermap, following pinned `zf(F,L)->filtermap(F,L)` and avoiding a stale alias wrapper after extraction. Other ListFunctions operations remain byte-exact after the new four-operation selection block, as asserted in extraction-proof.json. No public signature, registry stamp or module-state recheck is added.

# Classification boundaries

Finite2616-case success is necessary evidence, not a whole-contract proof on its own. Simple new/0, to_list/1 and is_empty/1 have small exhaustive source partitions and can be considered separately after their final source/native/registry evidence is bound. is_set/is_element/add_element/is_equal/del_element/binary set operators depend on total term comparison and native-equivalent recursion/argument roles. size depends on length/error-frame behavior. from_list and union/1 depend on the actual selected usort/umerge code, including reachable failure helpers for malformed inputs. map/filtermap depend on both callback kernels and sorting; fold/filter depend on callback invocation, exact type priority and source stacks.

Do not describe all21 as complete while source-reachable usort/umerge helper branches remain unported or unreviewed. A generic proper-list sorting result is insufficient evidence for the malformed-tail private-helper stack contract. Document pending/known dependencies per MFA if they remain after the current repairs. Existing API presence is21 independently of complete-contract status; the dynamic-dispatch change itself adds zero APIs.

This independent review inspected the proposed extraction, current frame helpers and admitted native difference categories. It performed no build, test, Main edit, GitHub action or classification mutation.
