# Compact oracle-progress proposal source review

Read-only review of five frozen proposal files, baseline1dc0f877dbf38ec7d9d58bf7cfca589f0b0d3c8b. All five hashes verified. No build, managed/native execution, Main or proposal edits performed. No source or comparison outcome changes found in the three new Program write anchors.

Checkpoint writes Source, the exact existing active OracleAbortEvidence object and completed comparison count before native ETF decode, managed compilation and managed execution. Each await completes before the potentially failing/stalled operation. The count excludes the active comparison, so it is a count of previously completed comparisons rather than proof of this native result passing. OracleExecutionPipeline yields ordered completed native outputs; its starting callback resets active evidence before waiting for the next output. No parallel sidecar writes are introduced by this ordered consumer.

The temporary file is next to the final path, WriteAllTextAsync closes it before File.Move(overwrite), and the replacement is on the same filesystem. Normal readers get the previous or new complete JSON; abrupt interruption during temporary writing may leave an incomplete .tmp, which the always-upload workflow deliberately preserves. This is application-level atomic replacement, not a power-loss/fsync durability guarantee. A checkpoint I/O failure aborts the run through the existing infrastructure catch and retains active native evidence in the forced terminal report when that report can be written. It does not silently continue or change expected outcomes.

The large report frequency remains OracleReportCheckpoint CaseInterval64; this proposal adds only a compact three-stage module sidecar. Workflow always includes both progress files as well as authoritative differential/fd reports. The sidecar can remain at the last module stage after a module completed, while later diagnostics run, or after a complete successful run. Consumers must not infer an active hang, final count, complete status or a passing comparison from it; the terminal report/run metadata remain authoritative.

Concrete provenance limitation: OracleAbortEvidence contains decoded stdout/stderr strings and exit code, whereas OracleProcessOutput also retains raw byte properties. The sidecar faithfully serializes that existing evidence but does not preserve arbitrary invalid UTF-8 native stream bytes. ASCII ETF protocol text is retained, and supported stream fixtures use their own byte capture protocol; do not call these progress string fields universally byte-exact. Native startup/process timeout/nonzero-exit failures occur before the yielded successful captured result and consequently do not create the new sidecar stage; the last prior sidecar may persist. Expression/diagnostic tracks also remain outside these three module checkpoints.

No final-result flag is added. Name and stage live in NativeEvidence; Source and CompletedComparisons live alongside it. If future consumers need run identity/version/count schema or explicitly stale/completed progress indication, add those as separate evidence fields rather than changing comparisons. Reusing an output directory across runs can expose stale sidecars until the first completed module write; current workflow clean checkout prevents that usual path but standalone callers should not treat a preexisting sidecar as current-run proof.

No blocking compile-flow issue found by source inspection. Actual build and synthetic checkpoint/interruption probes remain pending. Original5-file proposal and existing failure snapshots are untouched.
