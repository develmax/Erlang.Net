# Historical system_profile dead-receiver fixture repair

Source-only one-case overlay; no Main edit, build, original OTP execution, SDK execution or Git mutation. The root reported an actual original-fixture timeout reproduction in iteration3 of its focus run; that execution evidence remains owned by the root and is not claimed as this author's validation.

The historical source spawned a process whose complete body was ok, then created a monitor and selectively received only DOWN with reason normal. Those are separate operations. Pinned OTP-29.1.1 erlang.erl lines4560-4562 defines DOWN reason noproc when the process did not exist at monitor creation. The native monitor path in bif.c775-801 creates the origin entry and sends monitor-down/noproc when target monitoring cannot be delivered. An immediately returning child can already be gone before monitor/2. The resulting noproc message does not match the historical normal pattern, and the unbounded receive can reach the outer fixture timeout.

The correction uses the same live-child setup as the adjacent owner-death case: the child waits for stop, the parent creates its monitor, then the parent sends stop. Pinned ref_man_processes.md507-511 guarantees ordering for signals from one entity to the same destination; monitor is sent before the stop message. The child cannot normally finish before the monitor is initiated. It then returns normally, and the parent still requires the exact matching DOWN reference/pid/normal reason. The receive now has after5000 -> error(no_down), matching the nearby lifecycle fixture's explicit diagnostic bound.

Only after that exact normal DOWN does the fixture call system_profile against the dead pid. The existing expectations remain untouched: error:badarg is required for the dead receiver, the subsequent profile query must remain undefined and the shared fixture outcome is still {ok,done}. Accepting noproc as a substitute was deliberately avoided: it would broaden the setup assertion instead of removing its race. Pinned erlang.erl10659-10670 provides spawn_monitor/1 via spawn_opt(...,[monitor]) as another valid atomic setup, but the selected handshake retains the existing spawn/monitor API dependency and adjacent-case pattern.
