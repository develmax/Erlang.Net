## Exhaustive term-kind partition

The valid guest ranks are number < atom < reference < fun < port < pid < tuple < native record < map < nil < list < bitstring. Current Rank matches this partition. Unsupported arbitrary user-defined .NET Term subclasses are hosting inputs without native Erlang counterparts; they are not a discovered Erlang-language ordering defect. FloatTerm rejects NaN and infinities, so CLR NaN.CompareTo differences are not a valid guest counterexample.

| Kind | Source comparison and current audit |
| --- | --- |
| Integer / finite float | Same-kind numeric comparison; mixed exact uses integer-before-float; mixed arithmetic compares exact double rational to arbitrary integer. IntegerFloat's significand/exponent decomposition is mathematically equivalent on every finite binary64 value including signed zero/subnormals. Exact float uses numerical order and distinguishes -0.0 before +0.0, matching sortable native bits. Giant integer construction resource caps belong to producing terms, not a discovered comparator branch defect. |

## Actual blockers and priority

1. **Source-proven: HAMT Ordering algorithm absent.** Ordering >32 falls through canonical NEW_UNIQ-key order, while native cmp_term uses hash leaf phases/collision tie-breaks and arithmetic FUN key order. NumericEquality's newly added own-layout path is separate and does not prove ordering. Next increment candidate is artifacts/termorder373-hamt-ordering-proposal1: reuse the exact owned hash layout/lease, add the pinned two-phase state machine, preserve scalar order and existing equality routes. It is prepared, unbuilt and unobserved.
2. **Source-proven dependency mismatch requiring a native witness: nested flatmap keys in Ordering with exact=1.** Current map branch selects ArithmeticKeyEntries for Ordering only when !exact. Native exact map comparison traverses stored physical key arrays, whose non-atom keys use arithmetic exact term order; canonical storage instead uses NEW_UNIQ for FUN identity. Construct nested maps containing swapped OLD_UNIQ/NEW_UNIQ local FUN keys to establish the precise reached case. Do not silently change global canonical storage or exact identity to fix it. This is separate from the Part373 HAMT-only candidate.
3. **Construction invariant gate: reference-alias map cardinality/physical key representation.** Existing native Part366 proves equal reference aliases can have different hashes and missed HAMT lookup. It does not by itself observe insertion cardinality. Before treating arbitrary map payloads as source-complete, compare alias insertion/update/decoding and stored-count cases in maps above32 and flat controls. This is a map model gate, not a reason to demand another VM's literal atom indexes/addresses.
4. **Full state binding review:** code-entry interning, own atom/export/node identity and node epochs must be consistently captured for maps; current arithmetic flat key view intentionally freezes construction-time order. The approved own-VM protocol is the correct acceptance model. Exact foreign VM heap snapshots, matching pointer bytes, physical allocator sizes and timing are not required by this audit.

No new scalar/reference/record/tuple/list fix is justified from this review. Correct source branches should be kept and sealed rather than rewritten to manufacture API delta. The remaining fifteen ordsets APIs inherit these general ordering/equality and source-continuation obligations; full registration and finite passing samples alone cannot promote them. Small next changes are the isolated HAMT source machine, then a focused nested-map physical-key witness/repair, followed by closing construction invariants and final proofs for each ordsets source branch.
