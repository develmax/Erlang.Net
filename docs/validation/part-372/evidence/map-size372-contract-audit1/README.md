## map_size/1

Pinned erts/emulator/beam/erl_map.c:146-180 partitions inputs exhaustively: flatmap returns stored size, HAMT returns its stored size, every other term sets the original value as fvalue and raises BADMAP, which becomes `{badmap,Original}`. Native size fits a small under its representability constraint. Current CoreModules map_size handler partitions MapTerm / every other term and returns Entries.Count or the original badmap reason through ErlangSizeErrorFrames.Invalid. Entries is a read-only captured array, so the count is constant time and cannot execute element callbacks, term ordering or internal cursor operations. There is no loop or acquired resource requiring a new progress/cancellation HOST.

Error metadata uses ProcessContext.CaptureNativeFailure -> RuntimeExceptionCapture.Call and RuntimeExceptionNames.Formatter: top erlang:map_size frame has the original singleton argument and `[{error_info,#{module=>erl_erts_errors}}]`; current execution-chain caller, source file/line, continuation coalescing, and Math.Max(1,BacktraceDepth) follow the already reviewed native capture framework. Existing SizeSourceLocationHostChecks checks exactly that metadata, map caller at line16, guard failure and depths default/0/1/2/8. No duplicate HOST is proposed.

Actual existing direct native evidence: Part371 `erlang371-erlang-old-comparison1/rows.json`, size_type group, 22 distinct map_size cases times six observations =132 strict fields. These include invalid term categories, map sizes0/1/31/32/33/257, guard failure, and non-tail error. The sixty comparison-group rows with map_size in their label concern comparison operators and are deliberately excluded from this count. Part370 final-new contributes `erlang370_size_locations` renamed_map_error and map_guard_failure, two values plus ten full stack profiles =12 strict fields. These 144 fields supplement a source branch argument; they do not settle arbitrary construction invariants.

**Do not promote the full API yet.** The preceding Part371 contract audit explicitly retained the map canonicalization and external-reference stored-word-count gate. Part366 original-reference-review/report.json proves native references with stored counts1..5 compare equal yet have distinct native HAMT hashes and lookup behavior. Current MapTerm constructor universally deduplicates through Dictionary<Term,Term>, and map operations/ETF construction use this canonical object. A direct count handler proof cannot prove that every reachable original map state retains its cardinality during construction/update/decoding. No observed insertion/cardinality counterexample is asserted here: the existing receipt establishes equality/hash/lookup, not insertion count. The next narrow original experiment should insert a second equal reference with a different stored word count into a >32-element map and compare map_size, map_get/find and keys before/after, including a same-prefix leaf case and a flatmap control. Resolve the invariant from pinned construction source and observations before full promotion. Raw cursor protocol emulation is not required by the count operation itself; preserving all guest-reachable map states is.

## size/1

Pinned erts/emulator/beam/erl_bif_guard.c:size_1 partitions tuple / bitstring / other. It returns tuple arity, floor(bit_size/8) for *any bitstring*, or badarg. It does not reject a non-byte-aligned bitstring and does not round its byte count up. The routine can produce a bignum if needed for the native byte-size word width. Current source must retain that distinction from byte_size/1 (which rounds up).

The previous Part371 source audit correctly leaves size/1, bit_size/1 and byte_size/1 pending the explicit representation/resource-model review: BitString.BitLength is Int32 and numerous constructors/slices accept Int32 lengths while native bitstrings use Uint. The existence of a correct arithmetic branch over representable BitString objects is not proof that all original guest construction and overflow/error-precedence contracts are preserved. TupleTerm uses a read-only array and Int32 count. Do not silently drop this already documented gate or infer promotion from binary module status. No new HOST duplication or production patch is justified by this conditional audit alone.

For this task, the defensible promotion candidates remain erlang:length/1 and ordsets:size/1, whose opaque-head immutable-tail induction is independent of map ordering, construction cardinality and bitstring-width constraints.
