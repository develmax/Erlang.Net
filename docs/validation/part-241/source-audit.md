The failures happen before map construction: list_to_existing_atom returns the supposedly fresh literal name and the catch-pattern assertion fails. Both report Expected and Actual show the same badmatch, while FixtureExpected remains done.

**Native compile-time cause:** pinned OTP-29.1.1/ad05823719d77c8faee87348ea39513d4e2f99c5 `lib/compiler/src/erl_bifs.erl` explicitly declares list_to_atom/1 pure. `sys_core_fold.erl:905-950` checks purity, checks all arguments are literals, then calls apply(Module,Name,Args) and abstracts the returned literal. Compiling a later list_to_atom("fixed name") can therefore intern that atom before run/0 and before its initial absence assertion. Merely writing a name as a string is insufficient; the earlier source review only checked Lexer string handling and missed original compiler evaluation.

**Separate SDK result-decoding effect:** Differential Program executes the original first, decodes its ETF result to `expected`, then compiles and executes the SDK module (Program.cs499-514). OracleResultProtocol.Decode calls ExternalTermFormat.Decode; its atom case creates Term.A, whose Atom constructor calls AtomNameRegistry.Register. The original badmatch contains the target atom, so decoding that result registers it in the SDK before its own absence check. This directly explains how both reports can fail identically even though standalone SDK focus/full passed. It is not evidence of SDK compiler BIF constant folding. No harness change or atom filtering is needed or proposed.
