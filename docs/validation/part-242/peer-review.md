## Concrete limits requiring follow-up

1. None of the three genuine successful bytecode fixtures exercises a non-tail `call` plus native allocate/deallocate continuation frame. Current `call` support uses a managed continuation stack, while Y/allocation execution remains unsupported. Do not promote that internal continuation contrast as independent proof of general native CP/frame semantics; add a genuine compiler-exported nested-call fixture when those frames are implemented.
2. Function-clause/BIF reasons are real, but complete native logical stack, tracing/saved-calls, code leases/current-old registry admission and transactional publication are not implemented for this host image. The current documentation explicitly retains execution-frame/lifecycle gaps. A host facade does not satisfy missing erlang prepare_loading/finish_loading APIs.
3. Prepare is not a pure atom-table observation contract: literal ETF decoding creates managed atoms. Do not claim its atom-table side effects or absolute indices equal native preparation. Raw InputSha256 is provenance only, not native module_info(md5), fun uniqueness or code identity.
4. Generic FunT/closure execution, receiver scheduling, on_load callback observation, optional line/debug metadata and native validator completeness remain absent. These are bounded scope limits rather than hidden registration stubs. Public Supports answers structural supported-subset capability; value-dependent errors/uninitialized register paths remain execution errors.

The pending full pipeline/source/package guards remain necessary. Future loader/native-resource integration must preserve these distinctions and acquire genuine on_load/closure evidence rather than relax host errors or return fabricated successful handles.
