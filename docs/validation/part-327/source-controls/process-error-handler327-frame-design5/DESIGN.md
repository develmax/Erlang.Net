# 327 design 5: selected-handler failure-frame alternatives

SOURCE ANALYSIS ONLY, 2026-10-16. No new implementation or execution. Published326 b51f050c287f3b91346e1d3e30e86061708fb035 remains the parent. Candidate3 5517D794 is a diagnostic candidate, not a functional PASS. Root has begun its isolated build; this document does not assume the result of that build or a future runtime RED.

The concrete problem is ordering, not whether a frame is present. Terms.ErlangException.WithStackFrame returns the same exception for ExplicitStackTrace; otherwise it PREPENDS a freshly constructed actual-MFA frame. Candidate3 uses it once at every selected-handler boundary. Inner selected callback failure is captured first; an outer selected callback subsequently prepends its own frame, predicting outer-before-inner for nested nonexplicit callbacks. The strict RunNestedFrames uses two distinct registered callback modules and a non-tail outer continuation, so no native error/1 argument-list assumption is needed. Allocator's B690 pinned audit separately supplies a same-source-handler error/1 contract accepting native arity3 or rich INNER arguments, plus the explicit error/2 companion. Neither is an executed original observation.

Pinned ad058 beam_common.c build_stacktrace saves the current/innermost activation before saved continuations. Normal continuations may expose arity, not retained argument values. error/2 explicitly supplied arguments make the first inner handler arguments observable; explicit traces must remain untouched. An outer tail call can legitimately remove its activation; every nested-order fixture must retain a real non-tail operation. No expectation requires two native full argument lists.

## A. Local append instead of prepend

Appending a fresh actual outer callback frame to an already captured inner callback trace preserves inner-before-outer and repeated/equal activations. It also handles a HOST callback throwing nonexplicit Nil: appending to Nil creates the actual callback frame. It does not require global Terms changes.

It is NOT a complete replacement for candidate3. Execution.CallRuntime currently catches ordinary source erlang:error/1 and RuntimeCallFrames.Capture prepends the requested erlang:error/1 frame. Before the registry captures the actual selected source handler, its exception therefore already has a nonempty BIF trace. Blind append, or `Nil ? prepend : append`, leaves erlang:error ahead of the actual source handler; the existing ErrorFramesBody contract requires the real handler as first frame. Nonempty trace is not proof that another handler boundary already captured it. It may instead be a source/BIF/callee frame or an explicitly supplied trace. Append must also preserve the real inner callee and legitimate caller continuations rather than flatten them.

Therefore reject blanket append as a functional fix. It can be an unexecuted alternative diagnostic, not an approved implementation. Never remove current handler-top or nested-order controls merely to make it pass.

## B. Inspect or deduplicate frame values

Reject `first MFA equals handler`, `any handler frame exists`, or matching full argument lists as a provenance rule. Recursive activations can have equal MFA and equal argument values; two legitimate frames must survive. Non-source callbacks may deliberately construct a nonexplicit stack. Source continuations may contain arity rather than arguments. An erlang:error-shaped tuple alone does not prove the compiler created that frame, or that the selected handler itself was the innermost source function. No syntactic frame heuristic can safely decide prepend versus append, strip a BIF frame, or identify an activation.

ExplicitStackTrace is an existing hard boundary. Preserve the exact exception/trace for explicit Nil/custom raises; never set it to true globally as a suppression flag, and never reconstruct explicit trace terms in this adapter.

## C. Typed per-invocation failure provenance

A genuinely typed internal outcome can distinguish uncaptured callee failure, captured actual handler activation, and explicit trace. A fresh activation identity allows repeated/equal values without equality deduplication. It could retain an innermost-first ordered activation sequence and actual-MFA metadata, then materialize the public ErlangException once at a reviewed public boundary. The local selection out-policy remains useful for suppressing ONLY the fictitious requested missing-MFA frame; it does not, by itself, provide this nested failure provenance.

The current unchanged callback contract is ErlangFunction(ProcessContext,IReadOnlyList<Term>) -> ValueTask<Term>. An arbitrary registered outer delegate may await another PUBLIC Registry.Call and receive only ErlangException. Once that public boundary projects an internal outcome to the unchanged exception, its typed capture provenance is lost before the outer selected callback catches it. A new local policy object belonging only to the outer call cannot recover which inner capture happened. The same problem exists for compiler source execution unless invocation data is explicitly threaded through its callback/continuation path.

Consequently, do not advertise a one-object local-policy change as a proven solution. A complete explicit protocol needs an end-to-end data-flow design covering generated ModuleDefinition.Register callbacks, Execution.InvokeAsync/local/tail/source-tail/runtime-tail paths, ErlangApplyDispatch, and existing public HOST callbacks. PublicCall must preserve catch(ErlangException) behavior, Reason/Class, explicit trace identity and normal admission/lease timing. A private wrapper exception escaping public Call would break that contract. An Exception.Data entry, global/registry weak map keyed by exceptions, or new AsyncLocal forwarding marker would be ambient exception metadata and is outside the approved constraints. No such mechanism is proposed for implementation here.

## Decision and bounded next step

There is no source-proven drop-in complete fix within the existing nine-production-path mechanism plus all unchanged public callback contracts and the ban on ambient/exception metadata. Keep candidate3 diagnostic-only and obtain actual isolated results before classifying the predicted defect as an executed RED. Root should choose a reviewed explicit capture protocol (with a concrete per-path data-flow proof), or explicitly reconsider the provenance constraints, before functional revision4. This is a scope decision, not permission to alter Terms or callback ABI implicitly.

An explicit-protocol proposal may need at least new Runtime outcome/activation types and a Compiler ModuleDefinition.Register entry variant beyond the current nine-path ceiling. Exact additional paths and a HOST compatibility route must be approved BEFORE implementation; no fixed path count or complete algorithm is asserted here. Default lookup, sourceOwners delayed admission, raw BEAM whitelist, native ABI and ordinary callees remain unchanged.

Required discriminators for any approved alternative: immediate/delayed HOST Nil error; source error/1 real handler top; same-source nested error/1 with non-tail outer and arity-compatible projection; distinct HOST outer/inner order; explicit error/2 projected arguments and error/3; explicit Nil/custom raises unchanged; repeated/equal actual activations; legitimate nested missing lookup and actual valid callee undef; caller-local policy isolation across concurrent actors; exact source owner/image lease across yield/error/cancellation with settled owned children. Broad existing compiler stack parity remains partial and is not silently rewritten by this slice.
