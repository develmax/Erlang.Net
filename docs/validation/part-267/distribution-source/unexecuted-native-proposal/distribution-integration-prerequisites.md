# Isolated HOST distribution source proposal

Seed d2daaab10d53a4988702c5bac4d352cf3cf00fb8. Source-only: no build, formatter execution, runtime test, original OTP execution, Main mutation or Core registration.

Nine new runtime files implement an opaque C# handle with a strong typed entry and per-manager monotonic generation; a lease reads through the manager and cannot revive retired entries. It is deliberately NOT a ReferenceTerm or Erlang dist_handle: serialization/ETF restoration and resource-kind promotion remain separate prerequisites, avoiding overlap with the concurrent loader/resource owner edits. No kernel identity, remote node or connected state is fabricated.

The manager maintains one controller per HOST channel and one channel per actual local ProcessContext. Its completion task retires the entry. Every operation rechecks the context belongs to the runtime, its stop token, Done task, actual runtime process membership and halt state. Reattaching a finished process is rejected; replacement generations cannot be retired by an old handle. HOST queue buffers snapshot caller memory into immutable BitStrings; queue payload bytes and maximum buffer count are bounded separately, including empty buffers. Counters describe accepted HOST packets and consumed HOST buffers only, not ERTS allocated queue memory.

Lock order is exclusively manager gate -> ProcessRuntime membership gate. No Main exit hook or resource lock calls the manager. The completion continuation acquires only the manager gate after runtime completion; system notifications execute after releasing the manager gate. An enqueue/arm which linearized before close may deliver a notice after close; native signal admission does not retract an already committed notification. Tests must check this as a committed notice, not require a false guarantee of notice retraction. A lease validates liveness on each snapshot rather than granting authority independent of controller lifetime.

Initial uncertainties and explicit exclusions:

- The source has not compiled. The SDK style tool is not run while Root owns heavy work; review/format/build after permission from Root.
- There is no atomic Main process-exit callback: the completion continuation and per-operation membership checks cover this HOST scope. Production integration must review exact process exit/halt admission ordering and manager disposal as a runtime-owned component.
- Input-handler transfer accepts a local PID identity without an explicit liveness check, following the audited native stage. RecordAcceptedHostInput is a HOST acknowledgment, not a decoder or Erlang put_data implementation; its accounting stage intentionally differs from the native pre-validation increment.
- No weak saved magic handle, ETF restore, port controller branch, net_kernel RPC, nodeup/nodedown, busy suspension/hysteresis, native memory counter, packet encoder/decoder, atom cache, fragments, authenticated handshake or node identity migration is implemented.
- Source focus checks cover live owner, duplicate attachment, foreign manager handle, option old-value sequence, duplicate empty-queue notification arm, immutable buffer bytes, bounded queue rejection, FIFO/empty drain, payload accounting, stale close versus replacement, lease disposal and actual controller completion. Revision 2 adds real actor callback commands for wrong active process/foreign runtime, input-owner transfer, zero-sized buffer bound, payload cap, 64 start-barrier arm/enqueue races, queued death cleanup, runtime disposal/halt and replacement with a distinct process while the dead controller's old callback remains explicitly blocked. All are unexecuted source proposals. Barrier readiness only proves both tasks reached the declared start barrier, not that a particular internal lock interleaving occurred.
- The native Erlang probe is a predeclared source hypothesis only. It uses the unchanged pinned gen_tcp_dist example and actual two-node transport. It does not compare injected HOST bytes to real wire packets or reinterpret native statistics as HOST payload counters. No native result or byte resource is invented.

Future build command after the Root slot is free: `dotnet build tools/Erlang.DistributionHostFocus/Erlang.DistributionHostFocus.csproj -m:1 --disable-build-servers`; then execute its DLL with CPU2 and capture stdout/stderr/exit. Preserve the source freeze before any repairs and record exact old/new source changes. After focus passes, add independent barrier/old-generation tests and source peer review. Only then propose Main import of HOST-only types and tests; Erlang API presence remains unchanged.

## Revision 2 source peer plan

Pinned candidate ProcessContext.cs:37 constructs Done with TaskCreationOptions.RunContinuationsAsynchronously. The manager's ExecuteSynchronously continuation therefore cannot run inline inside the runtime completion setter in this pinned implementation. Verify those exact baseline bytes in independent review; this is not a guarantee for arbitrary host callbacks or future task-source changes. No RuntimeGate -> ManagerGate callback is installed. Recheck this when proposing atomic exit/disposal hooks.

HostDistributionBuffer exposes IReadOnlyList<BitString>, not ReadOnlyMemory. Each input segment is copied by BitString's public span constructor; BitString's backing array is private, ToArray clones, and WriteTo writes bytes without exposing its array. MemoryMarshal.TryGetArray is inapplicable to the public output types. Revision 2 checks mutations of both supplied byte[] and exported clone leave queued bytes unchanged; reflection/unsafe internal manipulation is outside this public immutability contract. BitString remains sealed. ReadOnlyCollection prevents list-element replacement, and the underlying list is retained privately by the wrapper only.

The foreign-runtime PID test uses a distinct host constructor identity string because PID terms from two same-name/creation-zero HOST runtimes can be structurally indistinguishable. This neither starts distribution nor claims a remote transport. Context ownership rejection independently compares the actual runtime object. The death barrier deliberately distinguishes logical process Completion from body unwind; its finally releases the owned old body on every test outcome.

## Revision 3: zero-length segment admission

Independent revision 2 source review (distribution-controller-revision2-independent-source-review.json, SHA256 97555a09e94a8adeaff6085b1d66510574615825c55dd50fe25d2945c37e2ea8) identified a real missing dimension: payload bytes and buffer counts alone allow an arbitrarily large collection of zero-length BitStrings inside each buffer. Revision 3 adds the distinct HOST tuning parameter MaximumSegmentsPerBuffer=16, enforced during enumeration before allocating the next snapshot. The 17th segment fails with a domain diagnostic. This is a HOST resource policy, not an OTP protocol limit.

The manager additionally requires an explicit positive maximumQueuedSegments. Admission checks bytes, buffer count and segment count before changing the queue. Segment accounting includes empty segments and updates under the same manager gate on enqueue, dequeue and retirement. Snapshot exposes QueuedSegments distinctly from QueuedPayloadBytes. A zero-segment buffer is still bounded by the existing buffer-count limit.

Unexecuted permanent source controls declare 16 empty segments accepted and 17 rejected, a 16-segment zero-byte buffer filling the queue segment cap, rejection of one further empty segment without queue mutation, dequeue recovery, two eight-segment buffers filling the total cap, closure and fresh-generation recovery, and disposal rejection. Revisions 1 and 2 freezes remain immutable; revision 3 must receive source peer review and actual focused execution before any HOST foundation integration. No native expected outcome, native probe source or Core registration changes.
