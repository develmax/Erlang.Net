# Runtime library backend selection

## Declarative .NET project integration (Part389)

An ordinary project using the Erlang.Net.CSharp package can declare startup libraries directly:

```xml
<ItemGroup>
  <ErlangLibrary Include="lists" Backend="Managed" />
  <ErlangLibrary Include="queue" Backend="Beam"
                 Image="Otp/queue.beam"
                 Sha256="759B1FE208F8A0DE292147EB00FFCE98F929263ADCFCD4AABB485E3B3EB4538D"
                 Dependencies="lists" />
</ItemGroup>
```

`Image` is an explicit project-relative or absolute build input; `Sha256` is mandatory for Beam and must match its bytes. Managed entries have no image/hash/dependencies. Dependencies are semicolon-separated library names and must also be explicitly selected. The task validates the complete declaration before writing outputs. It copies immutable hash-named images and writes the versioned manifest last, preserving unchanged bytes/mtimes on warm builds. The ordinary copy/publish pipeline deploys these files. Conflicting output destinations are refused. Removing all library items from a previously configured build emits an empty selection instead of retaining its old manifest; `ErlangLibraryEnabled=true` also requests an explicit empty manifest in a fresh project.

```csharp
string path = Path.Combine(AppContext.BaseDirectory, RuntimeLibraryManifest.FileName);
RuntimeLibrarySelection libraries = RuntimeLibraryManifest.Load(path);
await using ProcessRuntime runtime = await ProcessRuntime.CreateAsync(libraries, cancellation);
```

The manifest reader validates version1, required fields, duplicate/unknown JSON properties, enum names, library/dependency declarations and image hashes before runtime creation. Image locations are relative to the manifest directory and must stay within it. There is no directory scan, PATH search, environment inference, download or runtime compilation. Invalid selected input never triggers managed fallback. SHA256 binds bytes, not the truth of an upstream provenance claim; retain compiler/source evidence separately.

Build, publish and local PackageReference workflows are demonstrated in [HelloOtpBackends](../examples/HelloOtpBackends/README.md). Retained `.beam` inputs need no installed Erlang compiler. For source-build inputs, the existing separately admitted `ErlangBeamSource` route remains explicit and runs before library collection; its generated image path and expected hash must be declared. This does not add parse-transform/on_load support or automatically compile every OTP source.

Original `lists` and `queue` retain five lists native primitive boundaries while their pure bodies execute as original BEAM in .NET. Existing C# alternatives remain available. The generated C#/IL path remains separate; it is not an implicit third value of the startup library selector. Current selectable names do not guarantee admission of every image. No runtime-critical erlang switch or live state migration is introduced.

## Programmatic selection

The ordinary `new ProcessRuntime()` constructor retains its existing managed library registrations. Use the asynchronous factory to select a backend before the runtime becomes available to callers:

```csharp
byte[] lists = await File.ReadAllBytesAsync(listsBeamPath, cancellation);
byte[] queue = await File.ReadAllBytesAsync(queueBeamPath, cancellation);
var selection = new RuntimeLibrarySelection([
    RuntimeModuleSelection.Beam("lists", lists),
    RuntimeModuleSelection.Beam("queue", queue, dependencies: ["lists"])
]);
await using var runtime = await ProcessRuntime.CreateAsync(selection, cancellation);
foreach (var library in runtime.LibrarySelection.Modules)
    Console.WriteLine($"{library.Module}: {library.Backend}, input={library.InputSha256}");
```

Images must be supported, valid BEAM modules. For a module with an existing managed backend, the selected image must preserve that module's public exports. BEAM-only collections start as genuinely new modules without an invented managed owner. The factory does not compile Erlang or download OTP. Its input bytes and dependency collections are copied. All requested images are prepared, checked and published as a batch; required pure-library import MFAs must resolve to explicitly chosen modules. A preparation or execution failure does not select a managed substitute.

For a mixed configuration, choose `RuntimeModuleSelection.Managed("lists")` and BEAM queue with an explicit lists dependency. Choosing BEAM lists and managed queue is also supported. Omitted modules retain their default registrations. Managed and Beam are available for lists, queue, proplists, ordsets, maps and binary. Additional BEAM-only names are sets, dict, orddict, gb_sets and gb_trees; requesting Managed for these is refused. This allowlist does not accept every possible upstream image. Runtime-critical modules such as erlang cannot be switched through this API.

[HelloOtpLibraries](../examples/HelloOtpLibraries/README.md) declares and executes all eleven original libraries in an ordinary .NET project. The dependency cycle between proplists and sets is selected explicitly and published atomically. Exact image hashes and dependencies are retained in its project and provenance file. Startup does not scan the adjacent original `.erl` files or infer missing dependencies. The example needs no original compiler or Erlang VM at execution time.

`ErlangLibrary` is an MSBuild item describing a startup library choice, not a C# class or a language. `Backend="Managed"` chooses the maintained C# registration; `Backend="Beam"` chooses an explicit hash-bound original image. `.erl` is a source input to the separate `ErlangBeamSource` build route, which requires an admitted original compiler and produces a `.beam`; that result is then explicitly selected as Beam. Source files do not form a third runtime backend. The generated C#/IL compiler route remains separate from this selector.

The original modules execute their pure Erlang bodies in .NET. Native stubs retain actual C# primitive bindings: lists5, maps12 and binary22. Map traversal/comparison and math:log are explicit runtime boundaries. Two erts_internal map-comprehension compiler helpers are explicitly registered runtime intrinsics, not native BIFs and not substitutions for the selected pure library modules. Their complete standalone stack/resource/scheduler contracts remain separately pending.

Finite original comparisons do not prove whole-module compatibility. Atom-key map iteration follows the runtime's own atom table, as requested; a concrete ordering in another VM is not copied into ours. The retained raw maps/proplists packet still exposes those cross-VM ordering differences. Complete state-independent terms/stacks and explicit own-state cursor/accumulator/chunk rules are tested separately, without stripping fields or frames. See OTP_BACKEND_PROGRESS for counts and remaining scope.

Qualified native BIF stubs keep the runtime primitives captured for the selected image. They are listed separately from its pure Erlang bodies. Startup removes the superseded bootstrap code generation using the ordinary checked purge protocol before returning. Images with on_load are refused by this startup path. Normal later module loading/purging remains a separate operation; no live-state migration is provided.

The factory token controls startup, not the lifetime of a successfully returned runtime. Failed startup shuts down the private runtime and drains its actor dispatcher after retirement begins. Cleanup failures are aggregated with the original failure. Dispose the successfully returned runtime through its normal lifetime owner.

`LibrarySelection` is an immutable receipt of startup: module/backend, actual code-image identity, BEAM input SHA256 (null for managed), module MD5, exports, native primitives, managed delegate assembly MVIDs and explicitly requested/resolved dependencies. It is not a live report of later code reloads, an inferred whole-program call graph, or a performance measurement. `ModuleRegistry` remains the authority for current loaded code.

Validation and remaining gates are recorded in the English changelog and WORK_PLAN. Registered API presence, finite scenario coverage and complete source-contract compatibility remain separate counts.

These tests do not exhaust scheduling or cover every module execution-lease boundary. See [local acceptance](validation/part-376/local-completion/README.md).
