## Handwritten or generated: decide before porting

Before proposing a family, inspect upstream file provenance and locate its generator, IDL/specification, tables and handwritten extensions. Pin the upstream commit plus every external input snapshot/tool version and applicable license/notice. When outputs are generated, the delivery unit is **generator plus coherent family**, not thousands of manually rewritten MFAs. Separate handwritten platform bridge, marshalling, object ownership/lifetime and event semantics from generated signatures/wrappers. Change generator/input sources, never hand-edit generated outputs. Require deterministic regeneration, clean repeated-output diff, signature/export crosswalk and representative behavior/error/lifetime tests; generation alone does not establish semantics.

For Erlang.Net, the reusable deliverable is a **reproducible generator/adapter utility**, versioned input descriptions, the pinned OTP snapshot, executable contracts, deterministic output and a drift check. Prefer reusing the upstream generator and its generated Erlang modules/wrappers wherever those can be compiled/executed on Erlang.Net in standalone production **without BEAM**. Do not rewrite generated Erlang into C# without a concrete supported-subset, ABI, ownership or deployment constraint. Where a necessary C/C++ runtime bridge cannot be reused, a managed C# backend/adapter is appropriate. A one-off collection of generated files is insufficient.

Every packet must separately state generator implementation language and host, input-description formats/snapshots, output language(s), and build-time versus production runtime dependencies. A temporary upstream Erlang/BEAM generation host does not imply a BEAM production dependency; standalone production still must run on Erlang.Net without BEAM. Check the cheaper generated-Erlang reuse route before choosing a backend; this is a rule for future packet decisions, not an instruction to replace the current handwritten proplists adaptation. Document one exact regenerate/check command with tool versions and input/output paths: regeneration recreates declared outputs, check mode fails on unexplained drift, and a clean second run proves deterministic output. No such utility/command or successful regeneration is claimed today; the assigned generator-family packet must deliver and exercise it, with licenses/notices and source provenance bound.

Each packet must name generated and handwritten directories and owners before implementation. Proposed package-relative layout: `generator/` for reusable utility/backend and manifests, `inputs/` for admitted descriptions/snapshots, `generated/erlang/`, `generated/managed/` or other declared output-language directories, `handwritten/` for bridge/marshalling/lifetime/events and `contracts/` for signature/export/behavior checks. These are examples, not newly created directories or mandatory C# output. Family owner maintains generator/input sources and regenerates outputs; nobody hand-edits generated files. Root owns integration into actual repository paths/shared registration. Handwritten runtime ownership/lifetime changes require independent source/contract review; generated signature parity cannot accept them implicitly. Include exact regenerate/check invocation and clean second-run/drift receipts in the handoff.
