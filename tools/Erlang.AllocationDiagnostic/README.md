# Separate Windows allocation diagnostic track

Source-only diagnostic proposal. A current-head Windows build provides actual Runtime/Terms DLLs; their loaded hashes and MVIDs are recorded. The failed267 ZIP contains reports, not DLLs, so byte identity with that failed build is unavailable and must not be inferred. This separate manual workflow is not a retry of the failed CI run.

Eight fresh bounded processes each create one fresh runtime and actor. The first measurement retains the existing4MiB test's one-warmup synchronous same-thread window before diagnostic reflection/delegates are initialized. Sixteen subsequent samples per attribution category isolate registry argument construction, prebuilt arguments, registered body and direct Portable2. No test, budget or independent expected hash is changed. A completed diagnostic may record an allocation outlier; it does not prove cause or native compatibility.

No managed event listener runs inside the measured process. External ETW allocation sampling can be a separate optional track, but a12KiB allocation may not cross the sampled quantum and no allocation stack is promised. Native-profiler attribution, if later needed, must keep preallocated unmanaged observer buffers and remain diagnostic evidence only. All reports/raw streams and build evidence upload even after failure.

Required peer/style/build/CLI controls precede publication. Diagnostic argument failure and existing-output refusal are distinct from production behavior. Synchronous/thread validity remains recorded in each row; invalid windows cannot become a passed production-budget claim.
