## Sealing and CI

Run seal.py --repository ROOT only after integration and final source changes.
It writes source-plan.json using fsync and an atomic rename. An existing plan can
be replaced only with its explicit current --replace-plan-sha256. It excludes its
own plan and all live outputs, preventing self-hash cycles. Tool bytes, fixtures and
historical raw goldens use Raw hashes with local -text attributes; external textual
helpers/workflow use declared TextLF, binary/C# dependencies use Raw. The optional
--staged-tree ROOT exists for root-owned review of the proposed mirrored tree.

The manual workflow has exact head + reviewed plan SHA inputs, separate Linux and
Windows matrix jobs with fail-fast disabled, one provider preparation per platform,
all admitted observations per provider, independent final-source managed controls, an
explicit joint success gate, and always-uploaded failure artifacts. It does not
replace existing validate.yml or run duplicated push/PR triggers. Original failure
cannot become a passing job through continue-on-error: the final gate requires both
original acquisition and final controls. Failed provider preparation skips dependent
original steps; independent managed controls can still run after source admission.

Additional observer groups can share this collector by adding immutable fixture
files and jobs.json entries {Module, Fixtures}; run/0 is the only observer entry.
Reseal after any change. No per-MFA collector duplication is necessary.
