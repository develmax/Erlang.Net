# Pinned native loader contrasts

This standalone development exporter declares ten scenarios before native observation. The raw/gzip loading scenario uses two fresh VMs, giving eleven VM executions. No SDK execution, production loader registration or ordinary-corpus change is made.

Arguments: installed OTP root, repository root, new output directory, verified source-build evidence. The installed original version and build-log digest must match OTP-29.1.1/ad05823719d77c8faee87348ea39513d4e2f99c5; five retained genuine inputs are checked against the immutable declarations. The separate workflow source-builds the pin, then runs this project.

The tool compiles the supplied wrapper with warnings as errors and records its genuine BEAM and original disassembly. `direct/1` calls the real erlang:call_on_load_function/1 remote operation. Native JIT flavor is mandatory for the predeclared apply contrast. Each operation preserves its original value or complete exception class/reason/stack as raw ETF and text before any projection/assertion. Callback monitors are established by spawn_monitor before notice or ACK, and the actual callback PID and DOWN are retained. Fresh pending exports are never invoked.

All independent expected projections are written in the Erlang source and copied plan. Failure, timeout, absent final stage and missing raw expected/actual data cannot become success. A failed scenario does not suppress later fresh VMs. Per-VM stdout/stderr/exit and file hashes are retained, with a report after each VM. A physical abort still yields its actual process exit and incomplete stage. The eleven disposable VMs own their resource cleanup; native GC reclamation, export-table concurrency and distributed resources are outside these ten contracts.

This proposal is source-only and unbuilt. No native result is claimed. Prepared on_load HOST and magic resource infrastructure remain separate; native has-onload metadata after consumption and padded reference identities must not be normalized to managed limitations.
